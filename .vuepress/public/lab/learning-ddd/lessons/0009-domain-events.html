Domain Event là gì?

Theo Martin Fowler, một Domain Event là một object ghi lại điều gì đó đáng chú ý đã xảy ra trong domain - immutable, đặt tên ở thì quá khứ (BookingConfirmed, không phải ConfirmBooking), và chỉ chứa đủ dữ liệu để nơi khác phản ứng, không hơn. 

// app/Domain/Scheduling/Events/BookingConfirmed.php
final class BookingConfirmed
{
    public function __construct(
        public readonly BookingId $bookingId,
        public readonly RoomId $roomId,
        public readonly DateTimeImmutable $occurredAt,
    ) {}
}

Aggregate ghi lại sự kiện, không tự phát nó

RoomSchedule (bài 3, 7) ghi nhớ việc gì vừa xảy ra, nhưng không tự gọi Laravel event dispatcher - vẫn giữ Domain sạch khỏi framework (bài 6): 

final class RoomSchedule
{
    /** @var Booking[] */
    private array $bookings = [];

    /** @var object[] */
    private array $recordedEvents = [];

    // ... reserve(), fromRows() như bài 7-8 ...

    public function confirm(BookingId $bookingId): void
    {
        $booking = $this->findBooking($bookingId);
        $booking->confirm();

        $this->recordedEvents[] = new BookingConfirmed(
            $bookingId,
            $this->roomId,
            new DateTimeImmutable(),
        );
    }

    /** @return object[] */
    public function releaseEvents(): array
    {
        $events = $this->recordedEvents;
        $this->recordedEvents = [];

        return $events;
    }

    private function findBooking(BookingId $id): Booking
    {
        foreach ($this->bookings as $booking) {
            if ($booking->id()->value === $id->value) {
                return $booking;
            }
        }

        throw new \DomainException('Booking không tồn tại trong RoomSchedule này');
    }
}

Application layer: chỉ phát event sau khi save() thành công

Interface cho việc "phát" sự kiện cũng đặt ở Domain, giống Repository (bài 6), để Application layer không phụ thuộc trực tiếp vào Laravel Event facade: 

// app/Domain/Scheduling/Events/DomainEventPublisher.php
interface DomainEventPublisher
{
    public function publish(object $event): void;
}

// app/Infrastructure/Scheduling/LaravelEventPublisher.php
final class LaravelEventPublisher implements DomainEventPublisher
{
    public function publish(object $event): void
    {
        event($event); // Laravel's Event::dispatch()
    }
}
// app/Domain/Scheduling/Actions/ConfirmBookingAction.php
final class ConfirmBookingAction
{
    public function __construct(
        private readonly RoomScheduleRepository $repository,
        private readonly DomainEventPublisher $events,
    ) {}

    public function execute(RoomId $roomId, BookingId $bookingId): void
    {
        $schedule = $this->repository->find($roomId);
        $schedule->confirm($bookingId);
        $this->repository->save($schedule); // (1) lưu trước

        foreach ($schedule->releaseEvents() as $event) {
            $this->events->publish($event); // (2) phát event sau khi lưu thành công
        }
    }
}
Vì sao phải lưu (1) rồi mới phát event (2), không phải ngược lại?
Nếu save() thất bại (lỗi DB, mất kết nối...) sau khi event đã phát, Payment/Notification đã "biết" một việc mà thật ra chưa hề xảy ra - Booking chưa được confirm trong DB. Luôn phát event sau khi thay đổi đã được lưu chắc chắn.

Payment lắng nghe - và tự xây model của riêng nó

// app/Domain/Payment/Listeners/CreateInvoiceOnBookingConfirmed.php
final class CreateInvoiceOnBookingConfirmed
{
    public function handle(BookingConfirmed $event): void
    {
        // Payment tự tạo Invoice của riêng nó, không tái sử dụng class Booking
        Invoice::createForBooking($event->bookingId, $event->occurredAt);
    }
}

Đăng ký trong app/Providers/EventServiceProvider.php như một listener Laravel thông thường. Đúng ý bài 4: Invoice chỉ cần BookingId + thời điểm - không cần biết TimeSlot hay logic "trùng giờ" tồn tại.
