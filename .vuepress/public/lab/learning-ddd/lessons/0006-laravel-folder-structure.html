Vì sao Scheduling nên được áp DDD tactical (Entity, Value Object, Aggregate) đầy đủ, còn Notification thì không?

Bài này trả lời câu hỏi còn treo từ bài 2: Booking, TimeSlot, RoomSchedule (những class PHP thuần, không kế thừa Eloquent) sẽ sống ở đâu trong một dự án Laravel thật, và Eloquent Model đóng vai trò gì?

Ba tầng, một hướng phụ thuộc

Ý tưởng lấy từ Brent Roose (Spatie) - "Laravel Beyond CRUD": tách code trong một Bounded Context thành 3 tầng. Quy tắc quan trọng nhất: mũi tên phụ thuộc chỉ đi một chiều - Infrastructure phụ thuộc Domain, Domain không bao giờ phụ thuộc Infrastructure hay Laravel. 

Infrastructure  ──depends on──>  Application  ──depends on──>  Domain
(Eloquent, HTTP,                 (Actions/UseCase,              (Entity, Value Object,
 Controller, Job)                 điều phối)                     Aggregate - PHP thuần)
Vì sao hướng này, không phải ngược lại?
Nếu RoomSchedule (Domain) import Illuminate\Database\Eloquent\Model, bạn không thể test invariant "không trùng giờ" mà không boot cả Laravel, cả database. Bài 2 đã cố tình viết Booking/TimeSlot không đụng Eloquent - đây chính là lý do.

Repository: cầu nối giữa Domain và Eloquent

Domain định nghĩa interface mình cần (không quan tâm nó được lưu bằng MySQL, Postgres, hay in-memory). Infrastructure implement interface đó bằng Eloquent. Domain không biết gì về Eloquent - đây là Repository pattern áp dụng Dependency Inversion. 

// app/Domain/Scheduling/Repositories/RoomScheduleRepository.php
interface RoomScheduleRepository
{
    public function find(RoomId $roomId): RoomSchedule;

    public function save(RoomSchedule $schedule): void;
}
// app/Infrastructure/Scheduling/EloquentRoomScheduleRepository.php
final class EloquentRoomScheduleRepository implements RoomScheduleRepository
{
    public function find(RoomId $roomId): RoomSchedule
    {
        $model = RoomScheduleModel::where('room_id', $roomId->value)
            ->with('bookings')->firstOrFail();

        // map dữ liệu Eloquent -> đối tượng Domain thuần
        return RoomSchedule::fromRows($roomId, $model->bookings);
    }

    public function save(RoomSchedule $schedule): void
    {
        // map đối tượng Domain -> ngược lại Eloquent, rồi save()
    }
}

Application layer: Action điều phối, không chứa business rule

// app/Domain/Scheduling/Actions/ReserveRoomAction.php
final class ReserveRoomAction
{
    public function __construct(
        private readonly RoomScheduleRepository $repository,
    ) {}

    public function execute(RoomId $roomId, TimeSlot $slot): BookingId
    {
        $schedule = $this->repository->find($roomId);

        $bookingId = $schedule->reserve($slot); // invariant nằm ở đây, bài 3

        $this->repository->save($schedule);

        return $bookingId;
    }
}
Điểm mấu chốt
ReserveRoomAction không tự kiểm tra "trùng giờ" - nó chỉ gọi $schedule->reserve(). Toàn bộ invariant vẫn nằm trong RoomSchedule (Domain), đúng như bài 3. Action chỉ lo "lấy dữ liệu ra, gọi domain, lưu lại" - đó gọi là Application layer: điều phối, không ra quyết định nghiệp vụ.

Controller lúc này rất mỏng - không còn giống Controller ở bài 1: 

class BookingController
{
    public function store(StoreBookingRequest $request, ReserveRoomAction $action)
    {
        $bookingId = $action->execute(
            RoomId::from($request->room_id),
            new TimeSlot($request->start, $request->end),
        );

        return back()->with('booking_id', $bookingId->value);
    }
}
