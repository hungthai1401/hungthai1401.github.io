Entity vs Value Object

Bài 2 · Domain-Driven Design cho dự án Laravel đặt lịch (booking)

Khởi động: nhớ lại bài 1

Ở bài trước, vì sao đặt rule "không trùng khung giờ" trong Controller lại là dấu hiệu của một vấn đề?

Nếu câu trên còn mơ hồ, quay lại Bài 1 trước khi tiếp tục - mọi thứ dưới đây được xây trên nó.

Hai loại "đối tượng nghiệp vụ" trong DDD

DDD chia các khái niệm trong domain thành nhiều loại building block. Hai loại nền tảng nhất - thứ bạn sẽ dùng trong mọi bài sau - là Entity và Value Object.

EntityValue Object
Được nhận diện bởiIdentity (một ID) - tồn tại xuyên suốt vòng đờiChính giá trị các thuộc tính của nó
Hai object bằng nhau khiCùng ID, dù thuộc tính khác nhauMọi thuộc tính giống nhau, dù là 2 instance khác nhau
Có thể thay đổi (mutable)?Có - trạng thái thay đổi qua thời gianKhông - immutable, thay đổi = tạo object mới
Ví dụ trong bookingBooking (có thể bị hủy, xác nhận...)TimeSlot, Money, Email

Theo Martin Fowler, điểm mấu chốt để phân biệt không phải "nó có nhiều thuộc tính hay không", mà là: bạn có cần theo dõi nó qua thời gian như một cá thể riêng biệt không? Nếu có → Entity. Nếu nó chỉ mô tả một giá trị, và hai giá trị giống nhau thì luôn tương đương → Value Object.

Xây TimeSlot - Value Object đầu tiên

Hai TimeSlot cùng giờ bắt đầu/kết thúc luôn là "cùng một khung giờ", bất kể chúng là 2 instance PHP khác nhau. Không cần ID. Immutable - nếu muốn "khung giờ khác", tạo object mới: 

final class TimeSlot
{
    public function __construct(
        private readonly DateTimeImmutable $start,
        private readonly DateTimeImmutable $end,
    ) {
        if ($start >= $end) {
            throw new InvalidArgumentException(
                'Thời gian bắt đầu phải trước thời gian kết thúc'
            );
        }
    }

    public function overlaps(TimeSlot $other): bool
    {
        return $this->start < $other->end
            && $other->start < $this->end;
    }

    public function equals(TimeSlot $other): bool
    {
        return $this->start == $other->start
            && $this->end == $other->end;
    }
}
Chú ý invariant trong constructor
Quy tắc "start phải trước end" không thể vi phạm được - nó nằm trong constructor. Không có cách nào tạo một TimeSlot "méo" trong hệ thống. Đây chính là ý tưởng "domain object tự bảo vệ chính mình" từ bài 1, áp dụng lần đầu vào code thật.

Xây Booking - Entity đầu tiên

Booking cần được theo dõi qua thời gian: nó có thể là "đang giữ chỗ", rồi "đã xác nhận", rồi "bị hủy" - vẫn là cùng một booking dù trạng thái đổi. Vì vậy nó cần một identity (BookingId), độc lập với giá trị các thuộc tính khác: 

enum BookingStatus
{
    case Held;
    case Confirmed;
    case Cancelled;
}

final class Booking
{
    private BookingStatus $status;

    public function __construct(
        private readonly BookingId $id,
        private readonly TimeSlot $timeSlot,
    ) {
        $this->status = BookingStatus::Held;
    }

    public function confirm(): void
    {
        $this->status = BookingStatus::Confirmed;
    }

    public function id(): BookingId
    {
        return $this->id;
    }
}

Hai Booking có cùng TimeSlot nhưng khác BookingId là hai booking khác nhau (ví dụ: một bị hủy rồi người khác đặt lại đúng giờ đó). Ngược lại, hai TimeSlot cùng giờ luôn là "cùng một khung giờ" - đó là khác biệt cốt lõi giữa Entity và Value Object.

Vì sao chưa dùng Eloquent Model ở đây?
Cố tình chưa cho Booking/TimeSlot kế thừa Model. Đây là các domain object thuần PHP - test được mà không cần database, không cần boot Laravel. Bài sau (cấu trúc thư mục) sẽ chỉ ra Booking này sống ở đâu, và Eloquent Model đóng vai trò persist nó ra sao.
