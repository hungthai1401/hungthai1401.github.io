Lesson 0011 · Lab thực hành

Lab: ProxySQL + PostgreSQL streaming replication + failover thật

~20 phút chạy tay. Lab này dựng đúng những gì Lesson 10 nói tới bằng code thật: 1 primary + 1 replica PostgreSQL streaming replication, ProxySQL route read/write, và một failover thật (promote replica, dừng primary) để xem pgsql_replication_hostgroups tự phản ứng ra sao. Tôi vừa chạy toàn bộ lab này thật, gặp 2 bug và đã sửa — số liệu dưới đây là kết quả thật.

Kiến trúc lab

Ở lab/0010-postgresql-first-setup/: 1 PostgreSQL primary + 1 replica (streaming replication qua pg_basebackup -R, chuẩn PG12+) + 1 ProxySQL (bản 3.0.10, thoả điều kiện ≥3.0.8 từ Lesson 10) + 1 container client có psql.

cd lab/0010-postgresql-first-setup
docker compose up -d
sleep 25   # đợi primary init, replica basebackup, proxysql khởi động

Bug #1 tôi gặp: pg_hba.conf không tự cho phép replication connection

Lần chạy đầu, container replica exit ngay với lỗi:

pg_basebackup: error: connection to server at "postgres-primary" ... failed: FATAL:
no pg_hba.conf entry for replication connection from host "...", user "replicator", no encryption

Nguyên nhânPOSTGRES_HOST_AUTH_METHOD=trust chỉ sinh ra rule cho database thường (khoá all) — pseudo-database replication mà pg_basebackup dùng không tự động được bao gồm, cần dòng riêng. Đã sửa bằng cách thêm script init-hba.sh (chạy như init script của Postgres) để append host replication replicator all trust vào pg_hba.conf.

Bug #2 tôi gặp: heredoc SQL không tới được psql

setup.sh lúc đầu chạy "thành công" (không lỗi) nhưng không bảng nào được tạo. Nguyên nhân: docker exec thiếu cờ -i nên không forward stdin — heredoc SQL "bay vào hư không", psql chạy với input trống, không báo lỗi gì. Đã sửa bằng cách thêm -i vào mọi lệnh docker exec cần nhận input qua stdin.

Bước 1 — Xác nhận streaming replication hoạt động

docker exec lab10-postgres-replica psql -U postgres -tAc "SELECT pg_is_in_recovery();"   # kỳ vọng: t
docker exec lab10-postgres-primary psql -U postgres -tAc "SELECT client_addr, state FROM pg_stat_replication;"

Kết quả thật: pg_is_in_recovery()=t trên replica, primary thấy streaming — replication đang chạy đúng.

Bước 2 — Cấu hình ProxySQL (song song 4 bước Lesson 3/10)

./setup.sh

Script chạy: thêm pgsql_servers (hostgroup 0=primary, 1=replica) → cấu hình monitor user → thêm appuser → thêm pgsql_replication_hostgroups. Kết quả cuối script:

 hostgroup_id |     hostname     | port | status | comment
--------------+------------------+------+--------+---------
 0            | postgres-primary | 5432 | ONLINE | primary
 1            | postgres-replica | 5432 | ONLINE | replica

Kiểm tra monitor thấy đúng vai trò từng node:

-- monitor.pgsql_server_read_only_log
postgres-replica | read_only=1
postgres-primary | read_only=0

Bước 3 — Test read/write split thật

psql -h proxysql -p 6133 -U appuser -d appdb -c "INSERT INTO notes (body) VALUES ('hello from proxysql');"
psql -h proxysql -p 6133 -U appuser -d appdb -tAc "SELECT inet_server_addr(), body FROM notes;"

Kết quả thật: write đi vào primary (không lỗi), read (đã thêm query rule ^SELECT → hostgroup 1) trả về địa chỉ IP của replica — xác nhận qua so sánh với client_addr trong pg_stat_replication. Đúng như thiết kế của pgsql_query_rules ở Lesson 10.

Bước 4 — Failover thật: dừng primary, promote replica

docker stop lab10-postgres-primary
docker exec lab10-postgres-replica psql -U postgres -c "SELECT pg_promote();"

ProxySQL tự phản ứng thế nào — số liệu thật, poll runtime_pgsql_servers mỗi 2 giây:

Thời điểmhostgroup 0 (writer)hostgroup 1 (reader)
Trước failoverpostgres-primary (ONLINE)postgres-replica (ONLINE)
Ngay sau promote (~2-10s)postgres-primary (ONLINE) + postgres-replica (ONLINE)postgres-replica (ONLINE)
~12s sau (primary bị ping timeout 3 lần)postgres-primary (SHUNNED) + postgres-replica (ONLINE)postgres-replica (ONLINE)

Điều đáng nhớ nhất của lab nàyNgay khi pg_is_in_recovery() trên postgres-replica chuyển từ true → false, ProxySQL tự thêm nó vào hostgroup 0 — nó không rời khỏi hostgroup 1, vì pgsql-monitor_writer_is_also_reader=true (default). Primary cũ không bị gỡ ngay — nó vẫn "ONLINE" cho tới khi monitor ping đủ số lần thất bại (pgsql-monitor_ping_max_failures=3) mới chuyển SHUNNED. Đây chính là độ trễ failover thật bạn cần biết khi tính SLA — không phải tức thời.

Write sau failover — không sửa gì ở phía app, vẫn cùng 1 câu lệnh — tự động đi vào node vừa promote:

psql -h proxysql -p 6133 -U appuser -d appdb -c "INSERT INTO notes (body) VALUES ('written after failover');"
-- INSERT 0 1 — thành công, xác nhận trực tiếp trên postgres-replica (giờ là primary) thấy đủ 2 dòng

Dọn lab

cd lab/0010-postgresql-first-setup
docker compose down -v

So sánh với failover MySQL bạn đã học

Về bản chất, đây là đúng bài học ở Lesson 4-5 (MySQL) áp dụng lại: proxy layer tự phát hiện role đổi qua monitor check (read_only ở MySQL, pg_is_in_recovery() ở PostgreSQL), và có độ trễ thật (không tức thời) trước khi route traffic đổi theo. Khác biệt: PostgreSQL không tự "bầu" primary mới như Galera/Group Replication — bạn (hoặc Patroni/repmgr) phải chủ động gọi pg_promote(); ProxySQL chỉ phản ứng theo, không tự quyết định ai là primary.

Có bước nào trong 4 bước trên bạn muốn thử biến thể khác (ví dụ nhiều replica, hoặc tắt pgsql-monitor_writer_is_also_reader để xem writer không nhận traffic đọc), hỏi thêm tôi. Muốn đi tiếp: quay lại phần MySQL backend layer trên K8s còn treo từ Lesson 7, hay chủ đề khác trong mission?
