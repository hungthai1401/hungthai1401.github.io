Lesson 0006

Vận hành ProxySQL trên production

~12 phút đọc + quiz. Bạn đã có kiến trúc (Lesson 1-2), đã cấu hình được (Lesson 3), đã làm nó không SPOF (Lesson 4-5). Lesson này đóng nốt mảnh cuối: đổi config production mà không gây downtime, và biết ngay khi có gì bất thường.

Đính chính nhỏ từ Lesson 3

Ở Lesson 3, tôi nói ProxySQL có 3 lớp config (bảng chính → runtime → disk). Chính xác hơn là 4 lớp: RUNTIME, MEMORY (chính là "bảng chính" tôi nói), DISK, và CONFIG FILE — lớp cuối chỉ dùng lúc bootstrap lần đầu (proxysql.cnf, khởi động với --initial), không dùng để đổi config hàng ngày. Từ giờ tôi gọi đúng tên: MEMORY (không phải "bảng chính") để khớp thuật ngữ chính thức.

Rollback bạn đã có sẵn, không cần backup gì thêm

Đây là điểm hay nhất của kiến trúc 4 lớp: DISK luôn là bản "known good" cuối cùng bạn chủ động lưu. Nghĩa là:

  • Bạn sửa MEMORY, chạy LOAD ... TO RUNTIME, thấy sai ngay → chạy LOAD ... FROM DISK (nạp lại bản cũ) rồi LOAD ... TO RUNTIME lại — hoặc đơn giản hơn, restart ProxySQL, nó tự nạp từ DISK. Chưa mất gì, vì bạn chưa SAVE TO DISK.
  • Bạn đã SAVE TO DISK rồi mới phát hiện sai → hết đường rollback tự động. Đây là lý do quy tắc production quan trọng nhất là: không bao giờ SAVE TO DISK ngay sau LOAD TO RUNTIME — luôn có một khoảng quan sát traffic thật ở giữa.

Checklist đổi config1) Backup proxysql.db trước khi sửa lớn · 2) Sửa MEMORY bằng SQL · 3) LOAD ... TO RUNTIME · 4) Quan sát vài phút qua stats_mysql_connection_pool · 5) Ổn thì SAVE TO DISK, không ổn thì LOAD ... FROM DISK.

Ba bảng bạn nên nhìn mỗi ngày

Không cần dashboard cầu kỳ ngay từ đầu — 3 câu query này trả lời được hầu hết câu hỏi "có gì bất thường không?":

-- Node nào lỗi connection nhiều? Hostgroup nào quá tải?
SELECT hostgroup, srv_host, status, ConnUsed, ConnERR, Queries
FROM stats_mysql_connection_pool ORDER BY ConnERR DESC;

-- Query nào chạy nhiều/chậm nhất, đang route vào hostgroup nào?
SELECT hostgroup, digest_text, count_star, sum_time
FROM stats_mysql_query_digest ORDER BY sum_time DESC LIMIT 10;

-- Backend có đang bị flapping read_only không? (dấu hiệu bất ổn ở tầng MySQL)
SELECT * FROM monitor.mysql_server_read_only_log ORDER BY time_start_us DESC LIMIT 10;

Bật monitoring tự động (Prometheus)

Từ ProxySQL 2.x có exporter built-in, không cần cài thêm gì:

SET admin-restapi_enabled='true';
LOAD ADMIN VARIABLES TO RUNTIME;
-- http://<proxysql-host>:6070/metrics — trỏ Prometheus vào đây

Nếu chạy 3 node ProxySQL trên cùng máy (như lab Keepalived ở Lesson 5), mỗi node cần admin-restapi_port khác nhau, không thì service không start được. Và đừng scrape dưới 1 giây — metrics tính on-demand mỗi lần scrape, scrape dày không giúp gì.

Quiz — kiểm tra lại

1. Bạn vừa LOAD MYSQL QUERY RULES TO RUNTIME và thấy traffic route sai, nhưng CHƯA chạy SAVE TO DISK. Cách rollback nhanh nhất?

2. Vì sao quy tắc production nói không nên SAVE TO DISK ngay sau LOAD TO RUNTIME?

3. Bảng nào cho biết node MySQL nào đang bị lỗi connection nhiều hoặc hostgroup nào quá tải?

Đến đây, mission "ProxySQL cho production mission-critical" đã có đủ khung: kiến trúc, chọn topology, cấu hình, HA cho proxy layer, và vận hành an toàn. Nếu bạn đã có quyết định thật về hạ tầng (VM/Docker/K8s) hoặc topology MySQL, nói cho tôi để lesson tiếp theo đi thẳng vào chi tiết đúng bối cảnh đó — ví dụ cấu hình mysql_group_replication_hostgroups thật, hoặc thiết kế Terraform/Ansible cho stack này.
