Lesson 0003 · Lab thực hành

Cài và cấu hình ProxySQL cho read/write split

~25 phút, cần Docker. Đây là lesson tay-làm đầu tiên: bạn sẽ dựng 2 node MySQL (Async Replication — topology đơn giản nhất để lab, phần này bạn đã biết), rồi cấu hình ProxySQL thật để tự route read/write.

Vì sao lab với Async Replication trước

Bạn chưa chốt topology cuối cùng cho production (Lesson 2 cho bạn khung quyết định). Nhưng để học cách ProxySQL được cấu hình — bảng nào, lệnh nào, thứ tự nào — Async Replication là setup nhanh nhất để dựng lab, vì bạn không cần lo cluster quorum hay wsrep. Kỹ năng cấu hình mysql_servers, mysql_users, mysql_query_rules ở đây giữ nguyên khi bạn chuyển sang Group Replication hay Galera — chỉ có bảng monitor hostgroup đổi (xem lại Reference 0002).

Bước 1 — Dựng 2 node MySQL + 1 ProxySQL bằng Docker

File đã có sẵn trong workspace này, tại lab/0003-first-proxysql-setup/:

cd lab/0003-first-proxysql-setup
docker compose up -d
./setup.sh   # tạo replication user, trỏ replica về primary, tạo appuser/monitor user

setup.sh chỉ làm phần bạn đã biết (replication user, CHANGE REPLICATION SOURCE) — đọc qua để biết nó tạo user gì, vì ProxySQL sẽ cần đúng những user đó ở bước sau.

Bước 2 — Kết nối vào Admin interface của ProxySQL

mysql -u admin -padmin -h 127.0.0.1 -P 16032 --prompt 'ProxySQL Admin> '

Đây thực chất là một MySQL server giả — bạn dùng SQL để đọc/sửa config, không phải sửa file. Nhớ nguyên tắc 3 lớp: sửa bảng chính → LOAD ... TO RUNTIME → SAVE ... TO DISK. Quên bước nào, config không thật sự áp dụng hoặc không sống sót qua restart.

Bước 3 — Khai báo 2 backend server vào 2 hostgroup

INSERT INTO mysql_servers(hostgroup_id,hostname,port) VALUES (1,'mysql-primary',3306);
INSERT INTO mysql_servers(hostgroup_id,hostname,port) VALUES (2,'mysql-replica',3306);

Hostgroup 1 = writer (dự kiến), hostgroup 2 = reader (dự kiến) — nhưng ProxySQL sẽ tự xác nhận lại dựa trên read_only, không phải dựa vào con số bạn gõ.

Bước 4 — Cấu hình monitor user

UPDATE global_variables SET variable_value='monitor' WHERE variable_name='mysql-monitor_username';
UPDATE global_variables SET variable_value='monitor' WHERE variable_name='mysql-monitor_password';
LOAD MYSQL VARIABLES TO RUNTIME;
SAVE MYSQL VARIABLES TO DISK;

User monitor đã được setup.sh tạo sẵn ở bước 1 (quyền REPLICATION CLIENT). Đây là user riêng ProxySQL dùng để tự ping/kiểm tra backend — không phải user application.

Bước 5 — Khai báo writer/reader hostgroup theo read_only

INSERT INTO mysql_replication_hostgroups (writer_hostgroup,reader_hostgroup,comment)
  VALUES (1,2,'lab-cluster');
LOAD MYSQL SERVERS TO RUNTIME;

Đây chính là bảng đã nói ở Lesson 2 — cho Async Replication, ProxySQL chỉ cần đọc read_only: node có read_only=0 vào hostgroup 1, node có read_only=1 vào hostgroup 2. Kiểm tra ngay:

SELECT * FROM monitor.mysql_server_read_only_log ORDER BY time_start_us DESC LIMIT 5;

Bước 6 — Thêm user application

INSERT INTO mysql_users(username,password,default_hostgroup) VALUES ('appuser','apppass',1);
LOAD MYSQL USERS TO RUNTIME;
SAVE MYSQL USERS TO DISK;

default_hostgroup=1 nghĩa là: nếu không có query rule nào match, mọi query của appuser đi vào writer. An toàn hơn là default vào reader — tránh lỡ ghi nhầm vào node chỉ-đọc.

Bước 7 — Query rule cho read/write split

INSERT INTO mysql_query_rules (rule_id,active,match_digest,destination_hostgroup,apply)
  VALUES (1,1,'^SELECT.*FOR UPDATE$',1,1);
INSERT INTO mysql_query_rules (rule_id,active,match_digest,destination_hostgroup,apply)
  VALUES (2,1,'^SELECT',2,1);
LOAD MYSQL QUERY RULES TO RUNTIME;
SAVE MYSQL QUERY RULES TO DISK;

Rule chạy theo rule_id tăng dần, dừng lại khi gặp rule có apply=1 match. Rule 1 phải đứng trước rule 2: SELECT ... FOR UPDATE cần khoá dòng thật trên writer, nếu rule 2 (mọi SELECT ra reader) chạy trước, nó sẽ route sai.

Bước 8 — Xác nhận bằng traffic thật

mysql -u appuser -papppass -h 127.0.0.1 -P 16033 -e "SELECT @@hostname, @@read_only;"
mysql -u appuser -papppass -h 127.0.0.1 -P 16033 -e "SELECT @@hostname, @@read_only FOR UPDATE;" -e "BEGIN;" 2>/dev/null || true
SELECT * FROM stats_mysql_connection_pool;   -- chạy trong Admin interface, xem traffic vào hostgroup nào

Câu SELECT thường phải trả về hostname của mysql-replica. Nếu bạn tắt container primary (docker stop lab-mysql-primary) và chạy lại lệnh SELECT ... FOR UPDATE-style ghi, ProxySQL sẽ trả lỗi kết nối tới writer — vì Async Replication không có failover tự động (đúng như Lesson 2 đã nói). Đây là lúc bạn thấy rõ giới hạn thật của topology mình chọn để lab.

Quiz — kiểm tra lại

1. Bạn vừa sửa bảng mysql_query_rules và chạy LOAD MYSQL QUERY RULES TO RUNTIME, nhưng chưa chạy SAVE ... TO DISK. Điều gì xảy ra nếu ProxySQL process restart ngay bây giờ?

2. Vì sao rule chặn "SELECT ... FOR UPDATE" ra writer phải có rule_id nhỏ hơn rule route SELECT thường ra reader?

3. Nếu bạn tắt hẳn container mysql-primary trong lab này, điều gì xảy ra với các query ghi đi qua ProxySQL?

Nếu lab bị lỗi ở bước nào, dán log/lỗi cho droid ngay, đừng đoán mò. Lesson tiếp theo dự kiến: thiết kế ProxySQL tự nó có HA (ProxySQL Cluster + VIP) — để tầng proxy không phải điểm chết duy nhất, đúng như mục tiêu mission-critical trong mission của bạn.
