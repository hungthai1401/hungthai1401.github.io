Connection pooling & multiplexing trong ProxySQL

Đây chính là giá trị cốt lõi của proxy layerKhông có ProxySQL, mỗi app instance × mỗi worker/thread = 1 connection MySQL thật, tốn 1 OS thread bên MySQL (MySQL dùng "thread per connection"). Với multiplexing, hàng nghìn frontend connection có thể dùng chung vài chục backend connection.

Multiplexing hoạt động thế nào

ProxySQL mượn một backend connection đang free, cho 1 frontend session dùng để chạy 1 query, rồi trả connection đó lại pool ngay khi xong — session khác có thể mượn tiếp connection đó ngay, không cần đợi session đầu tiên "đóng kết nối".

Khi nào multiplexing TẠM bị tắt (tự bật lại được)

  • Transaction đang mở (tắt tới khi COMMIT/ROLLBACK)
  • LOCK TABLES / FLUSH TABLES WITH READ LOCK (tới khi UNLOCK TABLES)
  • SQL_LOG_BIN=0 (tới khi set lại =1)
  • Prepared statement qua binary protocol (COM_STMT_PREPARE) — tắt tới khi client đóng hết statement bằng COM_STMT_CLOSE

Khi nào multiplexing tắt VĨNH VIỄN cho session đó (nguy hiểm hơn)

  • GET_LOCK()
  • SQL_CALC_FOUND_ROWS
  • CREATE TEMPORARY TABLE
  • PREPARE stmt_name FROM '...' qua text protocol (khác binary protocol ở trên — text PREPARE không có cách bật lại, dù DEALLOCATE PREPARE)
  • Query có @ trong digest (session/user variable) — trừ 2 ngoại lệ hardcode: SELECT @@tx_isolation, SELECT @@version

Gotcha productionMột session vô tình chạy 1 trong các lệnh trên sẽ giữ riêng 1 backend connection cho tới khi session đó đóng — nếu ORM/driver của bạn làm điều này trên mọi connection trong pool phía app, connection pool hiệu quả ở backend co lại gần bằng số frontend connection, mất hết lợi ích multiplexing.

Tinh chỉnh multiplexing qua query rules

-- Không tắt multiplexing khi gặp SELECT @@max_allowed_packet (value=2: giữ nguyên trạng thái hiện tại)
INSERT INTO mysql_query_rules (active,match_digest,multiplex) VALUES
('1','^SELECT @@max_allowed_packet',2);

-- value 0 = luôn tắt multiplex cho query này, 1 = luôn bật

Pattern khoẻ mạnh (theo doc chính thức): ConnUsed thấp, ConnFree khá cao, Queries rất lớn — nghĩa là rất ít connection đang phục vụ rất nhiều query, đúng như mục đích multiplexing.

Sizing — cẩn thận với nhiều instance ProxySQL (HA/K8s)

mysql_servers.max_connections là giới hạn cho mỗi node ProxySQL riêng lẻ, không phải tổng toàn hệ thống. Có 3 node ProxySQL (Lesson 5 hoặc Lesson 7) × max_connections=100 mỗi node → backend MySQL thấy tối đa 300 connection đồng thời. Luôn tính: mysql_max_connections (MySQL) > số node ProxySQL × max_connections (mysql_servers).
