ProxySQL HA — Cluster + Keepalived/VIP

Sự thật cần nhớProxySQL không tự có cơ chế HA cho traffic của client. ProxySQL Cluster chỉ đồng bộ config giữa các node — không có VIP, không failover connection tự động. Bạn luôn cần thêm một lớp network riêng (Keepalived, load balancer, DNS) để client luôn trỏ vào node ProxySQL còn sống.

Hai việc cần làm, độc lập với nhau

ViệcCông cụGiải quyết gì
Đồng bộ config giữa các node ProxySQLProxySQL Cluster (native)Users, query rules, servers... giống nhau trên mọi node, không phải tự tay chạy Ansible mỗi lần đổi
Client luôn trỏ vào node ProxySQL còn sốngKeepalived + VRRP (VIP)Traffic failover khi 1 node ProxySQL chết

ProxySQL Cluster — lệnh cốt lõi

-- Trên 1 node đang chạy, thêm node mới vào danh sách Core
INSERT INTO proxysql_servers (hostname, port) VALUES ('10.0.0.5', 6032);
LOAD PROXYSQL SERVERS TO RUNTIME;
SAVE PROXYSQL SERVERS TO DISK;

-- Kiểm tra cluster đã thấy node mới chưa
SELECT * FROM stats_proxysql_servers_checksums;

Cần đặt cluster_username/cluster_password giống nhau trên mọi node (qua global_variables) để các node tin nhau khi đồng bộ. Lưu ý: kênh giao tiếp Cluster luôn là admin port MySQL protocol (thường 6032) — kể cả khi bạn chỉ đồng bộ config PostgreSQL (pgsql_*), xem Lesson 14.

Gotcha đã gặp thật (Lesson 14)Nếu 2 node cùng thêm nhau vào proxysql_servers ở đúng cùng epoch (cùng giây), Cluster báo Sync conflict, epoch times are EQUAL và dừng đồng bộ bảng đó. Khắc phục: chạy lại LOAD PROXYSQL SERVERS TO RUNTIME trên node muốn làm nguồn sự thật để tạo epoch mới.

Đã kiểm chứng cho PostgreSQL (Lesson 14)ProxySQL Cluster Sync (≥3.0.8) đồng bộ đầy đủ cả pgsql_servers, pgsql_replication_hostgroups, pgsql_query_rules, pgsql_variables — kể cả những bảng không được nêu tên rõ trong release note. Xem chi tiết ở Reference 0009.

Keepalived — pattern "single VIP" (active-passive)

# /etc/keepalived/keepalived.conf trên mỗi node ProxySQL
global_defs {
  lvs_id proxy_HA
}
vrrp_script check_proxy {
  script "killall -0 proxysql"   # health check: process còn sống không
  interval 2
  weight 2
}
vrrp_instance VI_01 {
  state MASTER          # 1 node MASTER, còn lại BACKUP
  interface eth0
  virtual_router_id 51
  priority 101            # node ưu tiên cao nhất giữ VIP khi mọi node đều sống
  virtual_ipaddress {
    192.168.0.88 dev eth0   # <-- VIP, application trỏ vào đây, không trỏ trực tiếp IP node
  }
  track_script { check_proxy }
}

Mỗi node đặt priority khác nhau (ví dụ 101/100/99). Node priority cao nhất còn sống giữ VIP. Khi nó chết, VRRP tự chuyển VIP sang node priority kế tiếp — theo benchmark thực tế, worst-case ~5s (phụ thuộc interval health check).

Ba pattern kiến trúc, chọn theo nhu cầu

PatternMô tảKhi dùng
Tile (App + ProxySQL cùng host)Mỗi app server có ProxySQL riêng, localGiảm network hop tối đa, nhưng khó quản lý nếu có hàng trăm app server (mỗi ProxySQL đều tự ping MySQL → MySQL bị "khảo bài" quá nhiều)
Single VIP (active-passive)N node ProxySQL, 1 VIP, chỉ 1 node nhận traffic lúc bất kỳĐơn giản nhất, đủ cho hầu hết trường hợp — chọn mặc định trừ khi có lý do cụ thể để phức tạp hơn
Multi-VIP (active-active)Nhiều VIP, mỗi VIP ưu tiên node khác nhau — nhiều node cùng nhận trafficCần tận dụng hết capacity của mọi node ProxySQL, đổi lại cấu hình phức tạp hơn (tránh trùng IP)
