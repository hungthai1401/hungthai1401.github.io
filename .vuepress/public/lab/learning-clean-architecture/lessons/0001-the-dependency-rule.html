Dependency Rule

Bài 1 / Clean Architecture + Laravel · ~10 phút

Bạn đã quen với layered architecture: Controller → Service → Repository → Database. Các layer xếp chồng lên nhau, dependency chảy từ trên xuống dưới. Đơn giản, trực quan — và đó cũng là vấn đề.

Clean Architecture của Robert C. Martin lật ngược một quy tắc duy nhất, và quy tắc đó thay đổi tất cả.

Quy tắc duy nhất: Dependency Rule

Dependency Rule

Dependency chỉ được chảy hướng vào trong. Code ở vòng trong không được biết gì về code ở vòng ngoài. Vòng ngoài có thể tham chiếu vòng trong, nhưng không bao giờ ngược lại.

Đó là toàn bộ quy tắc. Mọi thứ khác trong Clean Architecture — Entities, Use Cases, Ports, Adapters — đều là hệ quả của quy tắc này.

Bốn vòng tròn

Dependency chảy hướng tâm — từ ngoài vào trong, không bao giờ ngược lại
VòngChứa gìVí dụ trong Laravel
Entities Business rules cốt lõi, tồn tại độc lập với mọi thứ Class Order, Money (thuần PHP, không Eloquent)
Use Cases Logic của từng tác vụ cụ thể (application flow) CreateOrderUseCase, CancelOrderUseCase
Interface Adapters Chuyển đổi dữ liệu giữa Use Cases và bên ngoài Controllers, View Models, DTOs, Repositories (implements interface)
Frameworks & Drivers Công cụ, framework, I/O bên ngoài Laravel router, Eloquent models, MySQL, Redis, Mail

Khác gì với Layered Architecture?

Trong layered architecture truyền thống, OrderService thường gọi trực tiếp OrderRepository (Eloquent). Business logic phụ thuộc vào database. Đổi database → sửa business logic.

Trong Clean Architecture, Use Case không biết database là gì. Nó chỉ biết một interface (Port). Vòng ngoài (Infrastructure) implement interface đó. Dependency chảy vào trong.

Layered (truyền thống): dependency đi xuống

// Controller phụ thuộc Service, Service phụ thuộc Repository (Eloquent)
class OrderController {
    public function store(Request $req) {
        $order = new Order($req->all());
        $order->save();  // Eloquent trong controller. Lộn xộn.
    }
}

Clean Architecture: dependency đi vào trong

// Vòng TRONG: Use Case chỉ biết interface, không biết Eloquent
interface OrderRepository {
    public function save(Order $order): void;
}

class CreateOrderUseCase {
    public function __construct(
        private OrderRepository $repo  // ← Port, không phải Eloquent
    ) {}

    public function execute(CreateOrderInput $input): Order {
        $order = Order::create($input->items, $input->customerId);
        $this->repo->save($order);  // Gọi interface, không gọi DB
        return $order;
    }
}
// Vòng NGOÀI: Eloquent implements interface của vòng trong
class EloquentOrderRepository implements OrderRepository {
    public function save(Order $order): void {
        OrderModel::create([  // Eloquent ở đây, cách xa business logic
            'customer_id' => $order->customerId(),
            'total' => $order->total()->amount(),
        ]);
    }
}
Kết quả

CreateOrderUseCase không cần Laravel, không cần MySQL, không cần HTTP. Bạn có thể test nó bằng một FakeOrderRepository trong RAM. Đổi database? Viết thêm một PostgresOrderRepository. Business logic không đổi một dòng.
