Bài 3 / Clean Architecture + Laravel · ~10 phút

Bạn chắc đã viết một class OrderService với 15 method: create(), cancel(), refund(), applyDiscount(), sendConfirmation()... Nó phình to dần theo thời gian, và không ai muốn touch nó vì sợ vỡ chỗ khác.

Clean Architecture giải quyết vấn đề này bằng một quy tắc đơn giản: một Use Case = một hành động = một class. Không có "OrderService" khổng lồ. Chỉ có CreateOrderUseCase, CancelOrderUseCase, RefundOrderUseCase — mỗi cái đứng riêng, làm đúng một việc.

Use Case là gì, chính xác?

Use Case

Một class đại diện cho một hành động cụ thể mà người dùng (hoặc hệ thống) thực hiện. Nó điều phối (orchestrate) Entities và gọi các Port (interface) để hoàn thành hành động đó — không chứa business rule chi tiết (rule nằm ở Entity), không biết HTTP/Eloquent là gì (đó là vòng ngoài).

Nói cách khác: Entity biết "đơn hàng được hủy như thế nào" (rule). Use Case biết "khi hủy đơn hàng, phải làm những bước gì" (flow): lấy đơn hàng ra, gọi cancel(), lưu lại, gửi thông báo.

Input / Output: Use Case không nhận Request, không trả Response

Sai lầm phổ biến: truyền Illuminate\Http\Request thẳng vào Use Case. Làm vậy là kéo vòng ngoài (HTTP) vào vòng trong — vi phạm Dependency Rule ngay lập tức.

Thay vào đó, Use Case nhận một Input DTO (dữ liệu thuần) và trả về một Output DTO. Controller là nơi duy nhất biết Request tồn tại — nó đọc Request, tạo Input DTO, gọi Use Case, rồi chuyển Output DTO thành JSON response.

// app/Application/Order/CreateOrder/CreateOrderInput.php
final class CreateOrderInput {
    public function __construct(
        public readonly string $customerId,
        public readonly array $items,  // [['sku' => ..., 'qty' => ...], ...]
    ) {}
}
// app/Application/Order/CreateOrder/CreateOrderOutput.php
final class CreateOrderOutput {
    public function __construct(
        public readonly string $orderId,
        public readonly string $status,
    ) {}
}
// app/Application/Order/CreateOrder/CreateOrderUseCase.php
final class CreateOrderUseCase {
    public function __construct(
        private OrderRepository $orders,      // Port
        private InventoryChecker $inventory, // Port
    ) {}

    public function execute(CreateOrderInput $input): CreateOrderOutput {
        foreach ($input->items as $item) {
            if (!$this->inventory->isInStock($item['sku'], $item['qty'])) {
                throw new OutOfStockException($item['sku']);
            }
        }

        $order = Order::createNew(  // Entity tự áp dụng rule khi tạo
            CustomerId::fromString($input->customerId),
            OrderItems::fromArray($input->items),
        );

        $this->orders->save($order);  // gọi Port, không biết Eloquent

        return new CreateOrderOutput(
            $order->id()->value(),
            $order->status()->value(),
        );
    }
}

Controller giờ rất mỏng — chỉ là cầu nối:

class OrderController {
    public function __construct(private CreateOrderUseCase $useCase) {}

    public function store(Request $request): JsonResponse {
        $output = $this->useCase->execute(new CreateOrderInput(
            $request->input('customer_id'),
            $request->input('items'),
        ));
        return response()->json(['order_id' => $output->orderId, 'status' => $output->status]);
    }
}

Vì sao đáng công?

Test không cần HTTP, không cần DB

$useCase = new CreateOrderUseCase(new FakeOrderRepository(), new FakeInventoryChecker()); — chạy execute(), assert output. Không route, không middleware, không migration. Test chạy trong vài milli-giây.

Ngoài ra: mỗi Use Case là một điểm vào rõ ràng. Muốn biết hệ thống làm được gì? Đọc tên các file trong Application/ — đó chính là danh sách tính năng, không cần đọc controller lộn xộn.
