Ports & Adapters

Bài 4 / Clean Architecture + Laravel · ~10 phút

Ở Bài 1, bạn đã thấy OrderRepository là một interface, và EloquentOrderRepository implement nó. Bài này đặt tên chính xác cho hai thứ đó — Port và Adapter — và chỉ ra quy tắc quan trọng nhất mà người mới hay làm sai: ai được quyền định nghĩa interface.

Port là gì? Adapter là gì?

Port

Một interface định nghĩa những gì Use Case cần từ thế giới bên ngoài — không nói làm cách nào. Port được định nghĩa và sở hữu bởi vòng trong (Application), dù implementation của nó nằm ở vòng ngoài.

Adapter

Implementation cụ thể của một Port, nằm ở vòng ngoài (Infrastructure). Nó biết chi tiết kỹ thuật: Eloquent, Stripe SDK, cURL, SMTP...

Tên "Ports and Adapters" thực ra đến từ một architecture khác — Hexagonal Architecture của Alistair Cockburn (1994) — nhưng Uncle Bob dùng chính khái niệm này khi viết Clean Architecture. Hai cái tên, cùng một ý tưởng.

Quy tắc dễ làm sai nhất: ai định nghĩa interface?

Trực giác thông thường: viết StripePaymentGateway trước, rồi "trích xuất" interface từ nó (right-click → Extract Interface trong IDE). Đây là sai hướng.

Sai: Adapter định nghĩa Port

Nếu interface được sinh ra từ Stripe SDK, nó sẽ mang hình dáng của Stripe (ví dụ: method tên createPaymentIntent(), tham số theo format Stripe). Đổi sang PayPal? Interface không còn khớp — bạn lại phải sửa Use Case.

Đúng: Use Case định nghĩa Port theo ngôn ngữ nghiệp vụ

Port tên là PaymentGateway với method charge(Money $amount, PaymentMethod $method): PaymentResult — viết bằng ngôn ngữ mà Use Case hiểu, không mang dấu vết Stripe hay PayPal. Adapter phải "khuất phục" theo hình dạng này, không phải ngược lại.

Đây chính là Dependency Inversion Principle (chữ D trong SOLID) áp dụng vào architecture: interface thuộc về bên dùng nó (vòng trong), không thuộc về bên implement nó (vòng ngoài).

Ví dụ đầy đủ: PaymentGateway

// app/Application/Ports/PaymentGateway.php — Port, sống ở vòng Application
interface PaymentGateway {
    public function charge(Money $amount, PaymentMethod $method): PaymentResult;
}
// app/Application/Order/CreateOrder/CreateOrderUseCase.php — chỉ biết Port
final class CreateOrderUseCase {
    public function __construct(
        private OrderRepository $orders,      // Port #1
        private PaymentGateway $payment,     // Port #2
    ) {}

    public function execute(CreateOrderInput $input): CreateOrderOutput {
        $order = Order::createNew(/* ... */);

        $result = $this->payment->charge($order->total(), $input->paymentMethod);
        if (!$result->isSuccessful()) {
            throw new PaymentFailedException($result->errorMessage());
        }

        $this->orders->save($order);
        return new CreateOrderOutput($order->id()->value(), $order->status()->value());
    }
}
// app/Infrastructure/Payment/StripePaymentGateway.php — Adapter, chi tiết Stripe nằm hết ở đây
final class StripePaymentGateway implements PaymentGateway {
    public function __construct(private \Stripe\StripeClient $stripe) {}

    public function charge(Money $amount, PaymentMethod $method): PaymentResult {
        try {
            $intent = $this->stripe->paymentIntents->create([
                'amount' => $amount->toCents(),   // dịch Money → format Stripe cần
                'currency' => $amount->currency(),
                'payment_method' => $method->token(),
                'confirm' => true,
            ]);
            return PaymentResult::success($intent->id);
        } catch (\Stripe\Exception\CardException $e) {
            return PaymentResult::failure($e->getMessage());  // dịch Stripe exception → domain result
        }
    }
}

Nối dây trong Laravel: Service Container

Use Case cần một PaymentGateway, nhưng ai quyết định nó nhận StripePaymentGateway chứ không phải FakePaymentGateway? Laravel's Service Container, khai báo ở AppServiceProvider:

// app/Providers/AppServiceProvider.php
public function register(): void {
    $this->app->bind(PaymentGateway::class, StripePaymentGateway::class);
    $this->app->bind(OrderRepository::class, EloquentOrderRepository::class);
}

Khi Laravel resolve CreateOrderUseCase (ví dụ trong Controller constructor), nó tự động tiêm StripePaymentGateway vào chỗ interface PaymentGateway. Use Case không biết — và không cần biết — điều này xảy ra.

Vì sao đáng công: đổi Adapter mà không đụng Use Case

Test

new CreateOrderUseCase(new InMemoryOrderRepository(), new FakePaymentGateway(alwaysSucceeds: true)) — test luồng "thanh toán thất bại" chỉ cần FakePaymentGateway(alwaysSucceeds: false). Không gọi Stripe thật, không tốn tiền test, không cần internet.

Đổi provider

Công ty chuyển từ Stripe sang PayPal? Viết PayPalPaymentGateway implements PaymentGateway, đổi một dòng binding. CreateOrderUseCase không đổi một ký tự.
